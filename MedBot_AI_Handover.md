# Vitalis / MedBot AI — Project Overview, Prompt Engineering Guide и метрики успеха

**Репозиторий:** https://github.com/dimitry8st-prog/Vitalis-Medical-AI
**Версия документа:** 1.1
**Актуализировано:** 1 ноября 2026 года
**Назначение:** передача проекта новому специалисту без устных пояснений

Версия 1.1 синхронизирована с фактическим runtime после интеграции PR #12 и закрытия
privacy/security-пробелов. Исторические метрики ниже остаются целями, а не измеренными
результатами. Production-деплой этой версии отдельно не подтверждён.

## 1. Project Overview

### Цель проекта

Vitalis — MVP справочной AI-системы для поддержки клинических решений. Система должна помогать медицинскому специалисту быстро получить структурированный обзор по клиническому вопросу, сопоставить российские и международные рекомендации и увидеть использованные источники.

Vitalis не ставит диагноз и не заменяет врача. Окончательное решение всегда принимает медицинский специалист.

### Основные пользователи

1. Практикующие врачи — быстрый поиск диагностических и лечебных подходов.
2. Ординаторы и студенты медицинских вузов — разбор клинических тем и поиск источников.
3. Клиники и вузы — потенциальное корпоративное использование, API и локальное развёртывание.

### Ключевая ценность

- один интерфейс вместо ручного поиска по нескольким базам;
- отдельные контуры «РФ» и «Международные рекомендации»;
- RAG по локальному хранилищу Markdown-протоколов в `vault/`;
- дополнительный веб-поиск для проверки актуальности;
- структурированный ответ: определение, диагностика, лечение, реабилитация, предупреждения и источники;
- демо-режим без API-ключей и live-режим с внешними моделями.

### Что фактически реализовано

| Компонент | Реализация | Ответственность |
|---|---|---|
| Лендинг | `public/index.html` | Описание продукта и сбор заявок |
| Кабинет врача | `web/app.html` | Ввод вопроса и отображение ответа |
| Web-сервер | Node.js + Express, `server/` | Статика, заявки, прокси к AI API |
| AI API | FastAPI, `backend/app/` | Маршрутизация запросов и сбор ответа |
| База знаний | `vault/*.md` | Локальные протоколы и FAQ |
| RAG | FAISS, `backend/app/rag/` | Поиск релевантного контекста |
| РФ-контур | DeepSeek, отдельный системный контракт | Ответ только по российским источникам |
| Международный контур | DeepSeek, отдельный системный контракт | Ответ по WHO, NICE, ESC и другим allowlist-источникам |
| GigaChat | Отключённая заглушка | Не участвует в маршрутизации |
| Веб-поиск | DuckDuckGo / Serper / Tavily | Дополнение и проверка свежести источников |

### Основной поток данных

1. Пользователь отправляет вопрос из кабинета.
2. Node.js передаёт запрос через `/api/ai` в FastAPI.
3. Сервис классифицирует запрос как клинический или неклинический.
4. Для клинического запроса выполняется RAG-поиск; веб-поиск включён по умолчанию,
   но реально отключается параметром `use_web=false`.
5. Контекст и инструкции передаются в выбранный контур: `rf`, `intl` или `both`.
6. Ответ очищается от названий AI-провайдеров и преобразуется в карточку с разделами и источниками.
7. Интерфейс показывает российскую и международную версии ответа.

### Быстрый запуск

```bash
cp .env.example .env
npm install
npm start
```

В отдельном терминале:

```bash
cd backend
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Проверка:

- лендинг: `http://localhost:3000/`;
- кабинет: `http://localhost:3000/app`;
- FastAPI Swagger: `http://localhost:8000/docs`;
- состояние AI API: `http://localhost:8000/health`.

Без ключей следует оставить `LLM_MODE=mock`. Для реальных ответов требуется `LLM_MODE=live` и корректные ключи в `.env`.

## 2. Prompt Engineering Guide

Промпты находятся в `backend/app/services/ask.py`. Главные системные промпты — `RF_SYSTEM` и `INTL_SYSTEM`. Пользовательский вопрос и найденный контекст собираются методом `_user_prompt()`.

### Промпт 1: РФ-контур (`RF_SYSTEM`)

**Цель:** сформировать русскоязычный клинический обзор с приоритетом рекомендаций Минздрава РФ и российских профильных ассоциаций.

**Входные параметры:**

| Параметр | Тип | Назначение |
|---|---|---|
| `question` | строка, 3–4000 символов | Клинический вопрос пользователя |
| `mode` | `rf`, `intl`, `both` | Выбор контура ответа |
| `use_web` | boolean | Запрос на использование веб-поиска |
| `mkb` | строка или `null` | Необязательный код МКБ |
| RAG-контекст | список фрагментов | Релевантные материалы из `vault/` |
| Web-контекст | список результатов | Заголовок, фрагмент, URL, язык и предполагаемый год |

**Ключевые инструкции:**

- отвечать на русском языке;
- не раскрывать название модели или провайдера;
- для медицинских вопросов отдавать приоритет свежим веб-источникам;
- считать документы старше пяти лет потенциально устаревшими;
- заполнять применимые разделы фактами, а не пустыми заголовками;
- указывать источник и год;
- завершать медицинский ответ дисклеймером.

**Ожидаемый формат:**

1. Определение или суть вопроса.
2. Диагностика.
3. Лечение.
4. Реабилитация и прогноз.
5. Предупреждения и противопоказания.
6. Источники и дисклеймер.

**Ограничения:**

- для allowlist-первоисточников система пытается получить ограниченный релевантный
  фрагмент полного HTML/PDF; для остальных результатов доступен только сниппет;
- указанный моделью источник может не подтверждать конкретное утверждение;
- правило «старше пяти лет = устаревшее» слишком грубое: некоторые действующие рекомендации могут быть старше;
- промпт требует «полный обзор», даже если данных мало, что повышает риск неподтверждённых дополнений;
- наличие разделов не гарантирует медицинскую корректность дозировок и противопоказаний.

**Когда работает плохо:**

- редкие заболевания и узкие клинические ситуации;
- запрос без возраста, пола, анамнеза, симптомов или цели;
- запрос с персональными данными пациента;
- конфликтующие рекомендации разных лет;
- отсутствие свежих источников или сбой веб-поиска;
- вопросы, требующие экстренной триажной оценки.

**Рекомендованные улучшения:**

- запретить утверждение, если оно не связано с конкретным источником;
- возвращать структурированный JSON по схеме вместо свободного Markdown;
- добавить отдельные поля `evidence_level`, `source_url`, `source_year`, `uncertainty`;
- при недостатке данных сначала задавать уточняющий вопрос;
- отделить справочный обзор от персонализированной клинической рекомендации;
- проверять дозировки и противопоказания вторым независимым валидатором.

### Промпт 2: международный контур (`INTL_SYSTEM`)

**Цель:** дать русскоязычный обзор международных рекомендаций с приоритетом WHO, CDC, NICE, ESC/ERS, PubMed, Medscape и Mayo Clinic, при необходимости сопоставив их с подходом РФ.

**Параметры:** те же, что у РФ-контура. Отличается список приоритетных организаций и логика сравнения с российской практикой.

**Ключевые инструкции:**

- отвечать на русском языке;
- опираться на международные руководства и публикации;
- указывать факты, годы и источники;
- не оставлять пустые разделы;
- не раскрывать используемую модель;
- добавлять дисклеймер к медицинскому ответу.

**Ограничения:**

- правила разных стран могут быть неприменимы в РФ из-за регистрации препаратов, маршрутизации и стандартов помощи;
- терминология и классы доказательности у организаций различаются;
- поисковый сниппет может искажать контекст статьи;
- международный контур не гарантирует наличие полного текста платной публикации;
- автоматическое сравнение с РФ может смешивать независимые рекомендации.

**Когда работает плохо:**

- запрос относится к локальным приказам, льготам или маршрутизации пациента в РФ;
- нужен дословный разбор конкретной статьи или платной базы;
- пользователь ожидает персональное назначение;
- источник не содержит даты, версии руководства или уровня доказательности.

**Рекомендованный формат сравнения:**

| Клинический вопрос | РФ | Международный подход | Практическое отличие | Источники |
|---|---|---|---|---|
| Диагностика/лечение | Краткая позиция | Краткая позиция | Только подтверждённая разница | URL, организация, год |

### Правила изменения промптов

1. Не менять одновременно модель, RAG, веб-поиск и системный промпт: иначе невозможно определить причину изменения качества.
2. Каждую версию хранить под номером и проверять на одном и том же датасете.
3. Использовать слепую оценку: эксперт не должен знать, какая версия сгенерировала ответ.
4. Перед выпуском проверять не только полноту, но и фактическую подтверждаемость.
5. Любое улучшение основной метрики не должно ухудшать guard-метрику безопасности.

## 3. Метрики успеха

Текущие значения в репозитории не измеряются. Ниже — рекомендуемые метрики и стартовые цели для пилота; это целевые ориентиры, а не подтверждённые результаты.

### Главные метрики качества

| Метрика | Как считать | Цель пилота |
|---|---|---|
| Clinical completeness | Доля обязательных клинических пунктов, корректно отражённых в ответе | не менее 85% |
| Citation entailment | Доля утверждений, реально подтверждаемых указанным источником | не менее 90% |
| Критические галлюцинации | Ответы с выдуманной дозировкой, противопоказанием, источником или фактом | не более 2% |
| Source freshness | Доля медицинских ответов с актуальным источником и корректным годом | не менее 90% |
| Полезность для врача | Средняя слепая экспертная оценка по шкале 1–5 | не менее 4,0 |

**Рекомендуемая Primary-метрика:** Clinical completeness.  
**Guard-метрика:** доля критических галлюцинаций.  
**MDE для A/B-теста:** улучшение completeness минимум на 10 процентных пунктов без роста критических галлюцинаций.

### Технические метрики

| Метрика | Цель пилота |
|---|---|
| Успешные ответы API | не менее 99% |
| p95 полного ответа в режиме `both` | не более 15 секунд |
| p95 ответа одного контура | не более 10 секунд |
| Ошибки веб-поиска | не более 5% запросов |
| Ответы без источников | не более 5% медицинских запросов |
| Доступность сервиса | не менее 99,5% в месяц |
| RAG Recall@6 на размеченном наборе | не менее 80% |

### Бизнес-метрики

| Метрика | Что показывает | Начальная цель |
|---|---|---|
| Activation rate | Пользователь задал первый клинический вопрос | не менее 40% регистраций |
| Ответ признан полезным | Доля оценок «полезно» | не менее 70% |
| Повторное использование за 7 дней | Практическая ценность продукта | не менее 30% активированных пользователей |
| Конверсия лендинга в заявку | Эффективность позиционирования | 3–5% как гипотеза для проверки |
| Экономия времени | Разница с ручным поиском по самооценке врача | не менее 50% |

Для бизнес-метрик целевые значения должны быть уточнены после первых 50–100 пользователей; сейчас в проекте нет аналитических данных, подтверждающих эти показатели.

## 4. Основные риски и ограничения

### Риск 1. Медицинская ошибка или неподтверждённое утверждение

LLM может сформулировать убедительный, но неверный факт, дозировку или ссылку. Дисклеймер не устраняет этот риск.

**Снижение риска:** обязательная привязка утверждений к источникам, проверка источника, экспертная разметка тестов, запрет персонализированных назначений, отдельная проверка дозировок и критических противопоказаний.

### Риск 2. Устаревшие, неполные или несопоставимые источники

Локальный `vault/` содержит ограниченное число протоколов, а веб-поиск возвращает сниппеты. Российские и международные рекомендации могут относиться к разным популяциям и системам здравоохранения.

**Снижение риска:** реестр документов с датой пересмотра, организацией и статусом; загрузка официальных полных текстов; отображение даты и юрисдикции; ручное подтверждение ключевых отличий.

### Риск 3. Персональные данные и безопасность

Пользователь может вставить ФИО, контакты, номер карты или подробную историю пациента.
Обычные клинические запросы теперь проходят локальное обезличивание до веб-поиска и
модели; остаточные маркеры блокируют внешние вызовы. PDF имеют отдельный redaction и
review-gate. CORS использует явный список из `CORS_ORIGINS`, без wildcard.

**Остающийся риск:** regex-обезличивание не гарантирует удаление всех идентификаторов,
поэтому реальные данные пациентов не разрешены. До такого режима нужны юридическая
схема, пользовательская аутентификация/владение сессиями, аудит журналов и проверка 152-ФЗ.

## 5. Что проверить новому специалисту в первую очередь

1. Выполнить live-прогон 30 синтетических сценариев из `backend/evals/` и врачебную
   слепую A/B-оценку; сам набор и расчёт метрик уже добавлены.
2. Получить врачебное решение по кандидатам `vault/source_registry.json`; до статуса
   `approved` и `ingest_allowed=true` они не входят в RAG.
3. Добавить детерминированную проверку связи каждого клинического утверждения с
   конкретным фрагментом первоисточника, особенно для доз и противопоказаний.
4. Внедрить агрегированные метрики без текста запросов, алерты, rate limit и readiness.
5. Проверить сборку Docker, нагрузку, backup/restore и развернуть новую версию на VPS
   только после зелёного CI и приёмки.

## 6. Критерий готовности к пилоту

Проект можно передавать в ограниченный пилот только после выполнения четырёх условий:

- пройдён экспертный A/B-тест на размеченном наборе;
- критические галлюцинации не превышают установленную guard-границу;
- персональные данные удаляются до обращения к внешним сервисам;
- каждый клинически значимый вывод содержит проверяемый источник, организацию и год.

До этого Vitalis следует считать демонстрационным MVP, а не готовой медицинской системой поддержки решений.
