# Доведение Vitalis до production

## Целевой выпуск

Текущая допустимая цель — закрытый пилот для авторизованных врачей. Vitalis остаётся
справочной системой: он не ставит диагноз, не назначает лечение и не выполняет
автономных медицинских действий.

Публичный клинический сервис, работа с реальными медицинскими документами через внешний
LLM и заявления о клинической безопасности находятся вне текущего release scope.

## Обязательные ворота

| Gate | Критерий |
|---|---|
| Код | Python, Node, lint, dependency audit и container smoke зелёные |
| КР РФ | 17/17 PDF, `sync_status=complete`, SHA-256 и страницы |
| Life-OS | Только одобренные записи; автоматическая загрузка выключена |
| Privacy | Внешняя обработка документов выключена; персональные данные блокируются |
| Evidence | `EVIDENCE_GATE_MODE=strict`; неподтверждённые URL и дозы блокируются |
| Клиническая оценка | 30 синтетических сценариев, слепая оценка врачом, `release_gate_passed=true` |
| Эксплуатация | HTTPS, закрытая аутентификация, резервная копия и проверенный restore |
| Откат | Зафиксированы commit, image IDs, конфигурация и проверен возврат на предыдущую версию |

## Fail-closed release gate

После синхронизации КР и врачебной оценки:

```bash
PYTHONPATH=backend python backend/scripts/production_gate.py \
  --vault vault \
  --env-file /root/.config/vitalis-ru/python.env \
  --clinical-report /private/path/clinical-report.json \
  --variant candidate \
  --lifeos-manifest vault/generated/lifeos/portal/manifest.json
```

Команда не выводит секреты. Она блокирует выпуск при неполной базе КР, небезопасных
production-настройках, некорректном реестре, непроверенном Life-OS manifest или
непройденной клинической оценке.

## Порядок выкладки

1. Зафиксировать commit и собрать immutable candidate images.
2. Снять резервную копию текущих volumes и выполнить пробное восстановление в отдельном
   Compose project.
3. Развернуть candidate на loopback/staging, перестроить RAG и выполнить smoke-тесты.
4. Собрать ответы на 30 синтетических сценариев и получить слепую оценку врача.
5. Запустить production-gate.
6. Сохранить старые image IDs как rollback target.
7. Обновить закрытый пилот, проверить health, `/app`, контрольные запросы и логи.
8. При любой критической ошибке вернуть предыдущие images и volumes; не использовать
   `docker compose down -v`.

## Что ещё не является доказательством готовности

Работающий HTTPS, успешный ответ модели, наличие ссылок и зелёные unit-тесты сами по
себе не подтверждают клиническую точность, соответствие требованиям обработки
медицинских данных или безопасность для пациентов. Для расширения пилота нужны
юридическая оценка, модель угроз, мониторинг инцидентов, журнал версий источников и
регулярная повторная врачебная оценка.
